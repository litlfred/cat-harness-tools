# Caches

Every cache this layer declares (`cache/1.0.0`, `caches/`), and the key today's pins imply against the key the cache service holds. Staleness is computed, never claimed: a key that cannot be computed here, or a stored key nobody has read, is `undetermined`. Stored key, size, age and hit rate come from the daily cache report; without it those cells say so. Generated by `scripts/gen-caches-viz.ts`; do not edit.

### ci-image

**Prepared CI image: mounted layers, node_modules and Chromium** — cat-harness-tools, trust class a, owner CI speed 9 (bean folio-assistant-ay33); after the move, cat-harness-tools' shared ci-setup.

- **Holds:** Seven zstd layers in a FROM-scratch image: five workspace layers (every instance index.lock.json mounts, plus node_modules split by package and balanced by size) and two Playwright browser layers. The label ci-image.layers names each layer's role (ws\|pw). No secrets: public repos at locked commits, and npm through bun.lock.
- **Derived inputs:** Everything the image holds is a function of the key's inputs: the lock pins every mounted layer and its tree digest; bun.lock and package.json fix node_modules and through them Playwright's Chromium build; the recipe files fix how it is laid out; bun and the runner OS fix native modules. State branches are excluded by construction (prepare.sh strips every state-mount marker's directory).
- **Producer:** .github/workflows/ci-image.yml job publish (push to main touching the key's inputs, or workflow_dispatch); recipe .github/ci-image/build.sh → prepare.sh → docker buildx (zstd, provenance off); skips when the key's tag already exists
- **Consumers:** .github/actions/ci-setup (fast path), called by 13 Code-quality-gates jobs and Feature Staging's stage (folio-assistant#2964)
- **Save policy:** main or dispatch only (packages: write in the publish job alone); PR runs build into a throwaway local registry and never push
- **Verify:** fetch.sh hashes each layer's bytes while they stream and compares them with the manifest digest; then mount:lock:check re-hashes every mounted directory against the committed lock. Either failing → partial files removed, fallback path.
- **Uses:** `.github/actions/ci-setup/action.yml:61 key`, `.github/actions/ci-setup/action.yml:77 fetch`, `.github/actions/ci-setup/action.yml:82 verify`, `.github/workflows/ci-image.yml publish job`, `.github/ci-image/build.sh`
- **Notes:** Paths are folio-assistant's (#2961, branch claude/ci-image). Measured on a runner (run 42024357472): restore + mount:lock:check + bun install + Chromium launch = 7 s, against ~35 s of setup per job before (CQG run 42012108138). System libraries for Chromium (apt fonts) cannot be carried by a file image; `chromium: with-deps` still runs apt. Private package: consumers pass registry-token with packages: read (owner default, option 2). Hit/miss and why go to each job's step summary.

### layers-ref

**Layers cache ref: the composed overlay of a lock's pinned layers** — cat-harness-tools, trust class a, owner layers cache (session_01VQDpPg3qqw5ugnQBEYASrP), under cache-first CI.

- **Holds:** one commit whose tree is every locked directory, declaration and asset at its mount path, exactly as mount-from-lock lays it down (no node_modules, no state mounts, nothing built at publish)
- **Derived inputs:** the index's committed lock (index.lock.json), whose instances pin every layer's repository, commit, directories and digests
- **Producer:** the committer who changes the lock: mount:remote publishes it after a lock change, or `bun run cat layers:publish`; fallbacks: the re-pin train and the index's layers-cache workflow on main
- **Consumers:** mount-from-lock.ts (mount:lock), and through it .github/mount-from-lock.sh: the session-start hook, every CI job's mount, merge-main, the re-pin train, the prepared CI image build
- **Save policy:** written when the lock changes, by its writer; refused unless every mount hashes to the lock; pruned to the newest 20 lock refs plus main and every open PR's lock
- **Verify:** per instance, against the lock: the declaration's and each asset's sha256 and each directory's treeDigest (mount-from-lock layDownFrom); a layer that does not verify is fetched from its own repository, a missing ref falls back for all
- **Uses:** `scripts/mount-from-lock.ts:841 layersKey`, `scripts/mount-from-lock.ts:870 openLayersCache (reader)`, `scripts/mount-from-lock.ts:974 publishLayers (writer)`, `scripts/mount-from-lock.ts:1086 layersSummaryLine (hit/warm/miss)`, `scripts/remote-mount.ts:2141 the committer's publish after a lock change`
- **Notes:** Supersedes lpc-cat-mount and the other cat-mount Actions caches. Untrusted but exactly verified, so a stale or tampered ref only costs time. Measured on folio-assistant's lock (12 layers, ~32k files): 69 s per repository against 27 s on a hit with every byte verified. Lines are those of cat-harness-tools#1506 (head 05c346b). Every target needs it (it is the root of every needs closure), so it carries no `materializes`.
